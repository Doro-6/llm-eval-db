# 大模型需求抽取台账 · SQL 分析

把一份手工 Excel 台账（模型输出的需求清单 + 人工复核结论）重构为关系型数据库，用 SQL 复现并校验实验口径。

## 为什么做这个

原始台账有三个问题：

1. **散**：三次运行的输出在三个 sheet 里，跨表对比靠肉眼
2. **不可校验**：汇总数字（如「可追溯 10/14」）和明细是两张表，改一条明细，汇总不会跟着变
3. **问不出新问题**：想知道「无原文依据的条目最后都被怎么处置了」，只能手工筛

建库之后，这些问题都变成一句 SQL。

## 表结构（5 张）

| 表 | 存什么 | 行数 |
|---|---|---|
| `exp_run` | 每次模型调用的汇总（条数、污染数、可追溯数） | 3 |
| `requirement_item` | A 次运行的 15 条逐条明细（类别、紧急度、是否可追溯、处置） | 15 |
| `run_note` | 三次运行之间的差异（缺失/新增/KANO 判定变化） | 6 |
| `issue` | 模型输出的 8 类问题（F1–F8） | 8 |
| `prompt_iter` | 提示词迭代版本与效果 | 3 |

## 跑法

```bash
python run.py
```

零依赖（用 Python 自带的 sqlite3），会重建 `ledger.db` 并打印 7 组分析结果。

换 MySQL：把 `schema.sql` 的 `TEXT/INTEGER` 改成 `VARCHAR/INT`，`run.py` 换成 `pymysql` 连接，分析 SQL 基本不用动。

## 7 条分析 SQL 分别回答什么

| # | 问题 | 结论 |
|---|---|---|
| Q1 | 三次运行差多少 | 有效需求 14/12/15，可追溯率 71.4%–75.0% |
| Q2 | 汇总和明细对得上吗 | **一致（10 = 10）**，口径可信 |
| Q3 | 模型偏向判什么类型 | 期望型 50%、兴奋型 35.7%、基本型 14.3% |
| Q4 | 14 条最后怎么收敛的 | 并入 4 / 合并 3 / 删除 2 / 转待验证 1 / 转化 1 / 拆分 1 / 升级 1 / 保留降级 1 |
| Q5 | 哪些条目没有原文依据 | D-11、D-12、D-13、D-14 共 4 条 |
| Q6 | 问题类型与处置 | F1–F8 各自对应一个修复动作 |
| Q7 | 提示词改动值多少 | 可判定验收标准 0 → 6 → 22 条 |

## 数据来源

《大语言模型辅助需求分析与文档生成实验报告》表 10 / 11 / 12 / 13 / 18。
**库里的每一条记录都能在报告表格里找到对应行**，没有补写、没有估算。

B、C 两次运行只保存了报告已留档的汇总口径与差异事实，未逐条重建明细——因为原始输出没有逐条存档，不做推测。

## 可以继续做的
